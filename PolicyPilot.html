Elevator Pitch

Say this in 45–60 seconds. Then point at the architecture diagram.

“I built PolicyPilot - a Retrieval-Augmented Generation assistant for customer experience. Policy documents for shipping, billing, returns and support are chunked with overlap, embedded with a local sentence-transformers MiniLM model, and stored in ChromaDB. When a user asks a question in the Streamlit UI, I embed the query, retrieve top‑k relevant chunks, and generate an answer with local Ollama using a grounded system prompt that forbids inventing policies. The UI shows source citations so answers are inspectable. When policies change, I reindex documents - no model retrain.”

Full Workflow - Step by Step

If they say “walk me through it,” use Phase 1 ingest then Phase 2 ask.

Phase 1 - Ingest (offline / on reindex)

  • Read files from knowledge_base/
  • Extract text (incl. PDF via pypdf)
  • Chunk with overlap
  • Embed each chunk (MiniLM)
  • Upsert into Chroma + metadata

Phase 2 - Ask (online / every question)

  • User types question in Streamlit
  • Embed question (same model)
  • Top‑k cosine retrieve
  • Build grounded prompt
  • LLM answer + show sources

Ingest workflow (detailed)

I1
Load policy files

Read knowledge_base/ - shipping, billing, returns, support, faq (+ optional uploads). Formats: .md, .txt, .pdf.

↓
I2
Chunk with overlap

chunk_size=700, overlap=120. Prefer breaks at paragraph → sentence → space so meaning isn’t cut mid-thought.

↓
I3
Embed chunks

Local all-MiniLM-L6-v2 → ~384‑d normalized vectors. No embedding API cost; works offline after download.

↓
I4
Upsert Chroma

Store id + text + embedding + metadata (source, index) in persistent data/chroma/, collection policy_pilot.

Query workflow (detailed)

Q1
User asks in Streamlit

Chat input → pipeline.ask(question, top_k). Sidebar slider can change top‑k (1–8).

↓
Q2
Embed the question

Same MiniLM space as documents - otherwise similarity is meaningless.

↓
Q3
Top‑k retrieve

Chroma nearest-neighbor (cosine). Returns chunks + scores for the sources panel.

↓
Q4
Grounded prompt

System: answer ONLY from context; refuse if missing. User prompt = numbered context blocks + question.

↓
Q5
Generate + cite

Ollama generates the answer. If Ollama is down → extractive fallback (show top chunks). UI shows answer + sources.

RAG Concepts You’ll Be Asked

What is RAG?

Retrieve relevant external text, then generate an answer conditioned on that context. Knowledge lives in docs + vectors; the LLM reasons over retrieved evidence.

Why not fine-tune only?

CX policies change weekly. Retraining is slow/expensive. RAG: edit file → reindex. Fine-tune is better for style/format, not volatile facts.

Hallucination control

  • Grounded system prompt
  • Refuse if context insufficient
  • Show sources for verification
  • Still not 100% - bad retrieval can fail

Same embedding model

Query and documents must share the same MiniLM space. Different models → incompatible vectors → garbage similarity.

Cosine similarity
cos(θ) = (A · B) / (||A|| × ||B||)
MiniLM embeddings are L2-normalized → cosine ≈ dot product.
Higher score ⇒ more semantically similar chunk

Q: Does MiniLM use attention?
Yes - Transformer self-attention. Not TF‑IDF. Tokens attend to each other, then mean-pool to one sentence vector, then normalize for cosine search.
Q: Token embedding vs position embedding?
Token embedding: maps token ID → learned meaning vector. Position embedding: adds word order. Combined: x_i = e_token + e_pos, then attention mixes context.
Q: Why overlapping chunks?
Important sentences can sit on a boundary. Overlap keeps that context in at least one chunk so retrieval doesn’t miss it.

Defend Your Choices (Follow-ups)

Q: Why Ollama for generation?
Local and free - no API key. MiniLM is separate (embeddings only). If Ollama is down → extractive fallback from retrieved chunks.
Q: Which database? Where does data come from?
ChromaDB (vector DB). Source of truth is knowledge_base/ files. Ingest path: files → chunk → MiniLM → upsert Chroma. At ask time: embed question → NN search → LLM.
Q: Why Chroma not Pinecone/FAISS?
Chroma = persistent local + metadata + simple Python API for a portfolio app. Pinecone for managed prod scale. FAISS for raw ANN speed but more glue. Scaling path: Chroma → Pinecone/pgvector + hybrid search.
Q: How would you improve a wrong answer?
Debug order: (1) Was the right chunk retrieved? Fix chunking/embeddings/hybrid/rerank. (2) Context present but ignored? Strengthen prompt, lower temperature. (3) Ambiguous query? Rewrite/HyDE. (4) Add eval set (faithfulness/relevance).
Q: Grounded system prompt - what does it say?
Answer ONLY from provided context; if missing, say so and suggest support; don’t invent order IDs/fees/policies; be concise and mention policy limits when present.

Q&A Bank

Q: Walk me through PolicyPilot.
Use pitch + Figure A. End with: knowledge in docs/vectors; LLM only reasons over retrieved context; reindex updates knowledge.
Q: What did YOU implement?
Chunking, embeddings wrapper, Chroma store, ingest/reindex, Ollama generation + extractive fallback, pipeline orchestration, Streamlit UI (chat, sources, upload, reindex).
Q: RAG vs fine-tuning vs prompting?
Prompting: instructions only. RAG: external knowledge at inference. Fine-tune: change weights/behavior. For changing CX policies → RAG first. See RAG Drill for the full answer.
Q: What is top‑k?
Number of nearest chunks returned. Small k = precise but may miss; large k = more recall, noisier prompt, higher token cost. Default 4; tunable in UI.
Q: How do you know the system works?
Ask known policy questions; verify sources contain the claim; test refusal when KB lacks info; spot-check after reindex that new text is retrievable.
Q: Security / trust notes?
Don’t put real PII/secrets in knowledge_base for demos. Still verify critical financial/legal answers against original policy. Add auth/audit before production agent use.
Q: How does this map to ARC / document AI roles?
Same pattern: turn documents into embeddings, retrieve, generate grounded answers with citations - core of document intelligence and AI-ready knowledge systems.
Q: Challenge you faced?
Weak retrieval → wrong answers. Fixed via overlap chunking, grounded refuse-when-unsure prompt, and source panel so failures are visible instead of confident hallucinations.

RAG Interview Drill (say this)

Answers match what PolicyPilot actually does, plus what you’d add in production. Don’t invent hybrid search or formal IR metrics you never logged.

Q: Why RAG instead of fine-tuning?
CX policies (shipping, billing, returns, support) are external knowledge that changes often. Fine-tuning would bake facts into weights - every policy edit means retrain, cost, and lag.

RAG keeps facts in markdown/PDF, embeds them, and retrieves at ask time. I get citations (source + score in the UI), lower training cost, and updates by edit → reindex. Fine-tune is better for tone/format or a stable skill - not for volatile policy text. Prompt-only has no document grounding.
Q: How did you decide chunk size?
Defaults: chunk_size=700 characters, overlap=120 (config / .env). Not “500 tokens because industry standard.”

Policy docs are short sectioned markdown. ~700 chars usually keeps a policy rule (window, fee, eligibility) semantically complete in one chunk without blowing MiniLM’s useful context or stuffing the LLM prompt. Overlap covers ideas that sit on a cut. Chunker prefers paragraph → sentence → space breaks. If a rule split across chunks in debugging, I’d raise size or overlap - not blindly copy a blog number. Top-k default 4 fits a small local context window without drowning the grounded prompt.
Q: Which retrieval method did you use?
Dense retrieval only: embed query with MiniLM → Chroma nearest-neighbor (cosine) → top-k chunks + scores.

Why it fits: CX questions are often paraphrases (“how long for refund?” vs “refund timing”) - dense handles meaning better than pure keywords. Metadata (source file, chunk index) is stored and shown, but I do not filter by metadata at query time yet.

What I did not ship: BM25 keyword, hybrid, cross-encoder rerank. I’d add hybrid if exact SKUs/policy IDs fail dense match; rerank if top-k is noisy.
Q: How did you evaluate retrieval quality?
Today: manual / qualitative - ask known questions, open the sources panel, check that the cited chunk actually contains the claim; test “unknown” questions for refusal; after reindex, confirm new text is retrievable. Generation quality alone is not enough - a fluent answer can cite the wrong file.

What I’d add formally: a golden set of (question → expected source/chunk ids) and report Recall@K, Precision@K, MRR, optionally nDCG, plus a context-relevance label (human or LLM-as-judge). Separate retrieval metrics from answer faithfulness.
Q: How did you reduce hallucinations?
Stacked controls, not “better prompt” alone: (1) better retrieval + overlap so the right clause is in context; (2) grounding instructions - answer only from context; (3) refuse when context lacks the answer and suggest support; (4) citation panel so wrong grounding is visible; (5) no inventing fees/order IDs. Still not 100% - bad retrieval can still mislead; next: rerank + context validation before generate.
Q: What if the correct document is not retrieved?
In the app now: empty/weak context → model should say insufficient information; UI still shows whatever chunks came back so I can see the miss. Ollama down → extractive fallback of top snippets (not a fake answer).

Production fallbacks I’d add: query rewrite / HyDE, raise top-k or lower similarity cutoff carefully, hybrid BM25+dense, metadata filter (e.g. only returns.md), clarifying question, or handoff to a human. A production system must prefer “I don’t know” over a confident wrong policy.
Q: How would you debug a RAG answer that looks correct but is wrong?
Break the pipe: Query → Retrieve → (Rerank) → Context → Generate → Validate.

(1) Query: ambiguous? rewrite. (2) Retrieve: is the true clause in top-k? If no → chunking / embeddings / hybrid / k. (3) Rerank: if true doc is buried, add reranker. (4) Context: was the right text passed to the LLM? (5) Generate: context present but ignored → tighten prompt / lower temperature / force citations. (6) Validate: compare answer claims to cited snippets; fail if unsupported. Use the Streamlit sources panel as the first microscope.
Q: How do you know your retrieval is good?
Not from a fluent answer alone. I open the sources panel and check: (1) the cited file is the right policy domain (shipping vs returns); (2) the snippet actually contains the number/rule the answer used; (3) similarity scores for the top hit look clearly better than junk chunks; (4) “unknown” questions retrieve weak/irrelevant context and the model refuses instead of inventing.

That’s qualitative retrieval QA. Formal proof would be a golden set with Recall@K / MRR - I haven’t logged that yet.
Q: How many queries did you test?
Honestly: a small manual set, not hundreds. Roughly a handful per policy area (shipping, billing, returns, support) - about ~15–25 fixed questions I reuse after reindex, plus ad-hoc paraphrases while building the UI. Example prompts in Streamlit are part of that smoke set.

I do not claim a large offline eval suite. Next step: grow a golden CSV of 50–100 questions with expected source files.
Q: What did the failed queries have in common?
Patterns I saw when retrieval/answer missed: (1) vague queries (“what’s the policy?”) with no product/topic - dense search returns mixed files; (2) exact IDs / rare keywords that MiniLM underweights vs paraphrase wording; (3) answers that needed two sections (e.g. return window + refund timing) when top-k only pulled one; (4) questions about facts not in the KB - correct behavior is refuse, not a retrieval “win.”

Fixes that helped: clearer questions, overlap chunking, checking sources, and the refuse-when-unsure prompt. Remaining gaps point to hybrid/rerank and a labeled fail set.
Q: Your RAG answers correctly today. Tomorrow the source docs change - thousands of cached answers become wrong. How do you invalidate and refresh AI-generated knowledge safely?
Core idea: Treat generated answers as derived, not as the source of truth. Truth lives in the policy files + vector index. When docs change, reindex and make sure nothing still serves yesterday’s text.

What PolicyPilot does today: no persistent answer cache of “final truths.” Knowledge updates by edit markdown → reindex Chroma. Next ask embeds the query against the new chunks, so answers refresh naturally. The Streamlit reindex path is the safe refresh.

Production pattern I’d add if answers were cached (cost/latency):
  1. Provenance on every cache entry - cited doc_ids / chunk content hashes, kb_version (or index build id), generated_at, optional TTL.
  2. Version the KB - on reindex, bump kb_version (or per-file content hash). Invalidate any cache row whose version or overlapping doc_id no longer matches.
  3. Atomic index swap - build new collection → cut over → then purge stale answer cache (never serve mid-rebuild half-state).
  4. Lazy safety check - before returning a cached answer, re-hash cited chunks; if hash ≠ stored → regenerate from fresh retrieval.
  5. Prefer retrieve-at-ask for policies - safest default: don’t treat cached LLM answers as permanent facts; cache embeddings briefly if needed, regenerate grounded text.
  6. Smoke after refresh - known questions + citation check; UI can show “grounded as of <timestamp / kb_version>.”
One-liner: “Version the KB, store chunk hashes on any cached answer, reindex + atomically swap the index, and invalidate cache whose cited docs or kb_version don’t match - never serve AI text as immutable policy.”
Honesty line: “I ship dense RAG with grounded prompts and source inspection. Hybrid, rerank, and formal Recall@K are the next eval layer - not pretend they’re already in the repo.”
