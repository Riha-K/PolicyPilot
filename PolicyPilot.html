1. Why this project is important

Business value

  • Customers ask the same policy questions repeatedly.
  • Static FAQs are hard to search; agents waste time hunting SOPs.
  • A grounded assistant answers faster while staying consistent with policy.

Technical value

  • Shows you understand RAG, not only chat wrappers.
  • Separates knowledge updates (reindex docs) from model training.
  • Demonstrates embeddings, vector search, prompting, and a deployable UI.
One-line impact: Reduce support load and hallucination risk by answering from retrieved company documents instead of model memory alone.

2. Elevator pitch (30–45 seconds)

“I built PolicyPilot — a Retrieval-Augmented Generation assistant for customer experience. Policy docs for shipping, billing, returns, and support are chunked and embedded with a local sentence-transformers model into Chroma. When a user asks a question in Streamlit, we retrieve top‑k chunks and generate an answer with OpenAI or Ollama using a grounded system prompt. The UI also shows sources so answers are inspectable. Policies can be updated by editing files and reindexing—no model retrain required.”

Resume bullets tip: emphasize PolicyPilot · ingest → retrieve → grounded generate → Streamlit deployability.

5. Technologies — what & why (each one)

Python

language Main implementation language. Fast to prototype ML/LLM apps, rich ecosystem for embeddings and HTTP clients.

Why here: Glues Streamlit, Chroma, sentence-transformers, and LLM APIs in one codebase.

Streamlit

UI Turns Python scripts into interactive web apps with chat inputs, sidebars, and file uploaders.

Why here: Deployable interactive demo without building a separate React frontend. Good for interviews and Streamlit Cloud.

RAG (Retrieval-Augmented Generation)

pattern Retrieve relevant text first, then generate an answer conditioned on that text.

Why here: CX policies change; RAG lets you update docs instead of retraining. Also reduces hallucinations vs plain LLM chat.

sentence-transformers (all-MiniLM-L6-v2)

embeddings Converts text into dense vectors so similar meanings are close in vector space.

Why here: Local, free after download, strong baseline for English semantic search, small enough for demos.

ChromaDB

vector database Stores embeddings + documents + metadata and supports nearest-neighbor query.

Why here: Persistent local index with simple Python API; perfect for a portfolio/deployable Streamlit app.

In this project: persistent client at data/chroma/, collection policy_pilot, cosine space. Source text comes from knowledge_base/ (Chroma stores vectors after ingest — it is not the original policy source).

Chunking (overlap windows)

preprocessing Long documents are split so each vector represents a focused passage. Overlap preserves continuity across boundaries.

Why here: Embedding models have practical context limits; better chunks = better retrieval.

OpenAI API (optional)

LLM backend Hosted chat models via HTTP.

Why here: High-quality generation for cloud deploy when a key is available.

Ollama (optional/local)

LLM backend Runs open models locally and exposes a chat HTTP API.

Why here: Zero API cost local demos; privacy-friendly for sensitive policy text during development.

python-dotenv / .env

config Loads secrets and model names without hardcoding.

Why here: Clean separation of credentials from code; required for deployable apps.

pypdf

ingestion Extracts text from PDF policy documents.

Why here: Real CX teams often store SOPs as PDFs.

httpx

HTTP client Calls Ollama’s local API reliably with timeouts.

Why here: Simple, modern client for non-OpenAI generation path.

Cosine similarity (via Chroma distance)

retrieval math Measures angle similarity between normalized vectors.

Why here: Standard metric for semantic embedding search; scores help explain “why this chunk.”

6. Follow-up deep dives (from interview Qs)

F1. Why OpenAI AND Ollama? (two chat LLMs)

They are not used together. One path is chosen at runtime:

IF OPENAI_API_KEY is set
    → OpenAI-compatible chat API
ELSE
    → Ollama /api/chat (OLLAMA_BASE_URL + OLLAMA_MODEL)
  • OpenAI: easy for cloud deploy / Streamlit Cloud (laptop Ollama is unreachable from the cloud).
  • Ollama: free/local demo with no API key.
  • Same job: write a grounded answer from retrieved chunks.
  • Fallback: if neither works, show extractive top chunks (not a third LLM).

MiniLM is separate — it is the embedding model for retrieval, not the chat model.

F2. Which database? How does it work? Where does data come from?

Database: ChromaDB — a vector database (not Postgres/MySQL for this app).

Interview line: “Chroma doesn’t hold raw company knowledge by itself — we ingest policy files from knowledge_base/, embed them, and Chroma stores the vectors for semantic search.”
F3. Chunking, embedding, vector — what / how / which
StepWhatHow / which in this repo
Chunking Split long docs into overlapping pieces so retrieval is precise. app/rag/chunking.py — size 700, overlap 120; prefer paragraph/sentence breaks.
Embedding Turn each chunk (and later the question) into a dense number vector that captures meaning. sentence-transformers/all-MiniLM-L6-v2 via embeddings.py.
Vector / store Vector = the embedding; store finds nearest neighbors by similarity. ChromaDB at data/chroma/, cosine space, default top‑k = 4.
Generation Write the final answer from retrieved text. OpenAI or Ollama (see F1).

30-second pitch: Policies are chunked, embedded with MiniLM, stored in Chroma; at ask time we retrieve top similar chunks and only then call OpenAI/Ollama so answers stay grounded in docs.

F4. How MiniLM turns a chunk into an embedding (attention?)

Yes — it uses Transformer self-attention. Not TF‑IDF / bag-of-words.

1) Tokenize text → token IDs
2) Token embedding + position embedding → input vectors
3) 6-layer Transformer (multi-head self-attention + FFN)
4) Mean-pool token outputs → one sentence vector (~384-d)
5) L2 normalize (our code: normalize_embeddings=True)
   → ready for cosine search in Chroma

Attention (simplified): tokens look at each other with

Attention(Q,K,V) = softmax(QKᵀ / √d) · V

So “shipping” can attend to “days”, “standard”, etc., and get a context-aware representation before pooling.

F5. Token embeddings + position embeddings (step 2 detail)

Machines don’t understand words — they compute on numbers. After tokenization you only have integer IDs.

  • Token embedding: lookup table E_token[id] → dense vector (learned meaning starter for that subword/word).
  • Position embedding: lookup E_pos[index] → vector for order (Transformers don’t know sequence without this).
  • Combine: x_i = e_token(t_i) + e_pos(i) — that sum is the input to attention layers.

Token embedding ≠ the vocab ID itself. The ID is just a key; the embedding is the learned float vector. Context mixing happens next via attention, not in this step.

Say this: “Token embedding maps tokens to numerical vectors the network can process; position embedding adds word order; then self-attention builds context.”

A. Startup — how the pipeline is loaded

What: On first use, Streamlit loads the embedding model + Chroma store once and reuses them.

How: @st.cache_resource wraps get_pipeline() → creates RAGPipeline() → ensure_ready() (if Chroma is empty, ingest knowledge_base/ automatically).

Why: Loading MiniLM every click would be slow. Cache keeps one pipeline alive for the app process.

@st.cache_resource
def get_pipeline():
    pipe = RAGPipeline()
    pipe.ensure_ready()   # ingest KB if store empty
    return pipe
B. Chat — what it is and how it works

What: A conversational UI. User types a CX question; the app shows an assistant answer grounded in policies.

For what: Demo the full RAG loop to interviewers / users without a custom frontend.

How (step by step):

  1. Chat history lives in st.session_state.messages (list of {role, content, sources?}).
  2. User types in st.chat_input(...).
  3. App appends the user message, then calls pipe.ask(prompt, top_k=top_k).
  4. ask = embed question → Chroma top‑k → LLM (OpenAI/Ollama) with grounded prompt.
  5. Answer is shown with st.chat_message("assistant"); message saved back into session state.
result = pipe.ask(prompt, top_k=top_k)
# result keys: answer, backend, sources[{source, score, snippet}], ...

Top‑K slider: sidebar control (1–8) passed into ask so you can show how more/fewer chunks change answers.

C. Sources — what they are and why they matter

What: Provenance for the answer — which knowledge chunks were retrieved and how similar they were (score).

For what: Trust & interview demo. Shows the answer is grounded in docs, not free hallucination. Lets you debug bad retrieval.

How:

  • generate_answer returns sources: file path, cosine-ish score, short snippet.
  • In chat: expander Sources used under each assistant message (file + score).
  • Right panel Retrieved context: expanders with snippet text from st.session_state.last_result.

Score ≈ similarity (from Chroma distance). Higher ≈ closer match to the question embedding.

D. Reindex — what / why / how

What: Wipe the current Chroma collection and rebuild it from files currently in knowledge_base/.

For what: After you edit policy markdown (e.g. change return window), the old vectors would be stale. Reindex refreshes the search index.

How (button “Reindex knowledge base”):

  1. get_pipeline.clear() — drop Streamlit’s cached pipeline instance.
  2. Create pipeline again via get_pipeline().
  3. pipe.reindex() → ingest_knowledge_base(store, clear=True): delete collection → read all .md/.txt/.pdf in KB → chunk → embed → upsert.
  4. Show success counts → st.rerun() refresh UI.
if st.button("Reindex knowledge base"):
    get_pipeline.clear()
    pipe = get_pipeline()
    result = pipe.reindex()   # clear=True ingest of knowledge_base/
Reindex rebuilds from knowledge_base/ only. Extra files you uploaded earlier are not in that folder unless you saved them there — they may disappear after a full reindex.
E. Upload — what / why / how

What: Add an extra .txt / .md / .pdf into the live Chroma index without restarting the app.

For what: Interview demo: “Here’s a new policy snippet — ask a question that needs it.” Mimics real ops dropping a new SOP into the system.

How (uploader + “Ingest upload”):

  1. st.file_uploader accepts the file bytes in memory.
  2. Write bytes to a temp file (so ingest can use a real path + extension).
  3. pipe.ingest_file(tmp_path) → ingest_paths: read → chunk → embed → upsert (append into existing store, does not wipe KB).
  4. Success message with new chunk count → rerun.
uploaded = st.file_uploader(..., type=["txt", "md", "pdf"])
# save to tempfile → pipe.ingest_file(tmp_path)

8. Scenario-based interview questions

S1. Customer asks: “What is the electronics return window?”

Expected system behavior: Retrieve from returns.md, answer 15 days, mention accessories/seals.

Follow-up: “What if retrieval returns shipping instead?” → tune chunks, add synonyms, evaluate hit-rate, consider hybrid search.

S2. Policy changes tomorrow: express shipping becomes 1 day only in metros

Correct approach: Edit shipping.md → Reindex → no LLM fine-tune needed.

Why interviewers like this: Shows you know RAG’s operational advantage.

S3. Model invents a “₹500 goodwill credit” not in docs

Diagnosis: Hallucination / weak grounding.

Mitigations: stronger system prompt, lower temperature, require citations, refuse when context missing, add eval checks, optionally grounded decoding / stricter post-validation.

S4. Streamlit Cloud deploy but Ollama is on your laptop

Issue: Cloud app cannot reach localhost Ollama.

Fix: Use OpenAI/compatible hosted LLM in secrets, or host the model on a public endpoint/VPN.

S5. PDF is a scanned image; ingest extracts empty text

Issue: pypdf can’t OCR scans.

Fix: OCR pipeline (Tesseract) before ingest, or store a text layer PDF; keep sample KB as markdown for reliability.

S6. Latency is too high

Profile stages: embedding load (once), retrieval (usually fast), LLM (dominant). Cache embeddings model, reduce top‑k, use smaller/faster LLM, pre-warm Streamlit cache_resource.

S7. Two policies conflict (chat says 30 days, PDF says 15 for electronics)

Prefer more specific policy, improve chunk metadata, add document hierarchy, show sources to agent/user, fix source docs (source of truth).

9. Rapid-fire Q&A bank

QuestionStrong answer sketch
What is RAG? Retrieve relevant external knowledge, then generate conditioned on that knowledge.
Why not only fine-tune? Policies change often; fine-tunes are slower/costlier to update and can still hallucinate facts.
Why chunking? Improves retrieval precision; fits embedding model practical limits; overlap reduces boundary loss.
What does Reindex vs Upload do? Reindex: clear + rebuild from knowledge_base/. Upload: append one file into Chroma without wiping.
How does Streamlit chat call RAG? pipe.ask(question, top_k) → retrieve chunks → LLM answer; sources shown in chat + right panel.
Why OpenAI and Ollama? One chat backend at a time: key → OpenAI; else Ollama for local/free. MiniLM is embeddings only.
How do you evaluate? Retrieval recall@k, answer faithfulness, human CX review, golden question set.
Security concerns? Prompt injection via uploaded docs, secret leakage, PII in KB, auth on deployed UI.
Did you train a model? No by default—indexed docs + prompted LLM. Training is optional (see TRAINING_GUIDE).

10. Common interview traps (avoid these)

  • Saying “I trained Llama on PDFs” when you only did RAG indexing.
  • Claiming 0% hallucination because sources are shown (sources help, they don’t guarantee faithfulness).
  • Ignoring that embedding model and chat model are different components.
  • Not knowing your chunk size, top‑k, or distance metric.
  • Forgetting deploy constraint: local Ollama ≠ cloud availability.

Numbers to remember from this project

  • Default embedding model: sentence-transformers/all-MiniLM-L6-v2
  • Default chunk size / overlap: 700 / 120
  • Default top‑k: 4
  • UI entrypoint: streamlit run app/streamlit_app.py
  • Sample domains: shipping, billing, returns, support
